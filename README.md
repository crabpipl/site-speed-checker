# Аудит скорости загрузки страниц

Агент открывает страницы в браузере Chromium (десктоп и эмуляция смартфона), замеряет скорость загрузки и собирает отчёт:

- метрики Google Core Web Vitals (TTFB, FCP, LCP, TBT, CLS) и полное время загрузки;
- разделение на собственные скрипты сайта и внешние сервисы;
- запросы с ответом не 200 и сколько их пришлось ждать;
- самые долгие ответы 200 и что из них задерживало загрузку;
- рекомендации по каждой странице и итог по внешним сервисам: отключить, загружать отложенно или оставить;
- **сколько стоят внешние сервисы** — замер страницы с заблокированными внешними сервисами (всеми и самыми тяжёлыми по одному);
- **разбор LCP** на 4 части и **ответ сервера** по фазам (DNS, TLS, генерация HTML), признаки кэширования HTML;
- **неиспользуемый JS/CSS** по каждому файлу;
- **аудит картинок** (формат, размер, width/height, lazy, приоритет главной картинки) с оценкой экономии, **шрифты**, **размер DOM**;
- **источники сдвигов вёрстки** — какие элементы прыгают и на сколько;
- **SEO**: есть ли контент в HTML без JS, что получают Googlebot и YandexBot (статус, скорость, H1), robots.txt, title/description/canonical, микроразметка, одинаковые title на разных страницах;
- **сравнение с прошлой проверкой**: что ухудшилось или улучшилось, новые внешние скрипты и ошибки;
- **отклик на нажатия (INP)**: насколько быстро страница реагирует на кнопку «В корзину», фильтр, меню, галерею, поиск — и чьи скрипты при этом тормозят;
- **повторный визит**: первый и повторный заход на страницу рядом — насколько помогает кэш браузера и какие свои файлы зря скачиваются заново;
- **краткая сводка для руководства** (`summary.html`, включается в `settings.txt`, раздел 2.3): одна страница без технических деталей — общая оценка, ключевые цифры, 3–5 главных проблем — с выигрышем, если он измерен в этой проверке, или с тем, сколько проблема занимает сейчас, — и тем, кто их решает, изменения с прошлой проверки; можно распечатать или сохранить в PDF;
- **задачи для трекера** (`tasks.html`): все рекомендации, собранные в задачи, — одна карточка на проблему со списком страниц, приоритетом, исполнителем, выигрышем (если он измерен) и текущим значением; кнопки «Копировать» для переноса в трекер, отметка «перенесено»; то же таблицей для Excel — `tasks.csv`;
- **тестовый контур**: отдельный список тестовых страниц и команда `npm run audit:test` — отчёты и история теста отдельно от прода, лишние для теста проверки выключены, а каждая тестовая страница сравнивается с тем же путём на проде («тест против прода» перед релизом);
- **тест оформления заказа**: вход в личный кабинет по коду из SMS или письма (код вводится в Терминале), оформление настоящего заказа и замер каждого шага — от карточки товара до «Заказ оформлен»; после теста агент выходит из аккаунта и удаляет cookies;
- **сравнение с конкурентами** (включается в `settings.txt`, по умолчанию выключено): похожие страницы конкурентов замеряются в той же проверке — таблица «мы и конкуренты», место по скорости и кадры «что видит посетитель через 1, 2, 3, 5 с» на каждом сайте;
- **проверка по расписанию** на macOS, Windows и Linux: агент сам запускается, например, раз в неделю ночью, ведёт журнал и показывает уведомление с итогом;
- **бюджеты скорости**: пороги в файле `budgets.txt` (LCP, вес страницы, число внешних сервисов и т. п.) — в начале отчёта и в конце проверки в Терминале видно, какие страницы вышли за бюджет, впервые или повторно, и что вернулось в норму;
- **раскадровка загрузки**: что видит посетитель на экране во время загрузки — когда исчезает пустой экран, когда появляется главный контент, что прыгает; рядом — то же для повторного визита, когда файлы сайта уже в кэше браузера;
- **реальные посетители**: как страница работает у настоящих посетителей в Chrome (Chrome UX Report — данные, по которым Google ранжирует сайт), рядом с замером агента, с динамикой за полгода (нужен бесплатный ключ Google, раздел 1.4).

## Как устроена проверка страницы

Каждая страница проверяется дважды: в разрешении **десктопа** и **смартфона**. Смартфон эмулируется: Pixel 7 с каналом 1,6 Мбит/с и задержкой 150 мс (медленный мобильный интернет) и процессором, замедленным в 4 раза. Все файлы страницы делят этот канал, поэтому на тяжёлых страницах время на смартфоне — десятки секунд; условия замера указаны в отчёте, сводке и задачах. В каждом разрешении агент делает следующее.

1. **3 обычные загрузки** страницы в браузере Chrome, каждый раз с чистого листа (без кэша и cookies), как у нового посетителя. При каждой загрузке записываются:
   - метрики скорости Google: TTFB, FCP, LCP, CLS, TBT и время полной загрузки;
   - все запросы страницы: статус ответа, время, размер, свой это ресурс или внешний сервис;
   - сколько времени процессора занял каждый скрипт.

   В отчёт идёт **медиана** трёх загрузок, это защищает от случайных выбросов. Ошибки собираются по всем трём загрузкам.
   Во время первой загрузки агент дополнительно записывает кадры экрана — из них собирается **раскадровка** (лишних загрузок для этого не нужно).
2. **2 загрузки без внешних сервисов**: все сторонние скрипты (счётчики, реклама, чаты) заблокированы. Разница с обычной загрузкой показывает, сколько секунд стоят внешние сервисы.
3. **По 1 загрузке без каждого из 3 самых тяжёлых внешних сервисов.** Так видно вклад каждого из них.
4. **Повторный визит**: в одном и том же браузере страница открывается сначала для прогрева кэша, затем ещё 2 раза с замером — как у покупателя, который вернулся на сайт. Во время первого замера повторного визита записываются кадры экрана — это вторая лента раскадровки. Отчёт сравнивает первый и повторный визит по каждой метрике и показывает, какие файлы взялись из кэша браузера, а какие снова пошли в сеть и почему (по заголовку `Cache-Control`).
5. **Тест отклика на нажатия (INP)**: агент определяет тип страницы (каталог, карточка товара или другая) и нажимает несколько ключевых для этого типа элементов — не все кнопки подряд (подробно — раздел 2.1). Для каждого нажатия замеряется время до отрисовки результата и какие скрипты (свои или внешних сервисов) в это время выполнялись. Для любого сайта можно задать точный список нажатий в файле `actions.txt`. Всплывающие окна, которые перекрывают элементы, агент сначала закрывает — как покупатель — и отмечает в отчёте. Переходы по ссылкам во время теста блокируются.
6. **1 загрузка для замера неиспользуемого кода**: какая доля JavaScript и CSS скачивается, но не нужна для показа страницы.
7. **SEO-проверка**: агент запрашивает HTML страницы так, как его получают браузер, робот Google и робот Яндекса (без выполнения JavaScript), и проверяет `robots.txt`.
8. **Данные реальных посетителей** (если подключён ключ, раздел 1.4): агент запрашивает у Google статистику Chrome UX Report по этой странице за последние 28 дней — для компьютеров или смартфонов, в зависимости от разрешения проверки. Если у страницы мало визитов, берутся данные по сайту в целом. Это несколько секунд и не нагружает сайт.
9. **Страницы конкурентов** (только если включено сравнение с конкурентами, раздел 2.4): после своих страниц агент замеряет похожие страницы конкурентов — те же обычные загрузки, раскадровка и данные реальных посетителей, но без углублённых тестов (пункты 2–7).

Затем агент анализирует собранные данные:
- делит ресурсы на свои и внешние;
- находит ответы не 200 и самые долгие ответы 200;
- раскладывает LCP на составляющие;
- проверяет картинки, шрифты и размер страницы (DOM);
- находит элементы, из-за которых прыгает вёрстка;
- сравнивает результат с прошлой проверкой этого сайта;
- сопоставляет замер с данными реальных посетителей: совпадает ли картина, что ухудшилось за полгода;
- сверяет результат с бюджетами из `budgets.txt` (раздел 2.2).

Итог — список рекомендаций по приоритету.

**Сколько длится:** около 7 минут на страницу в одном разрешении, то есть примерно 14 минут на страницу с двумя разрешениями. Каждая страница конкурента (если сравнение включено) добавляет около 2 минут в каждом разрешении. Быстрый режим (`--quick`) пропускает пункты 2–6 и занимает около 2 минут на страницу в одном разрешении.

**Важно:** это замер с одного компьютера и одной сети. У реальных посетителей цифры могут отличаться, поэтому результаты лучше сравнивать между собой в динамике, а для оценки «как у людей» смотреть раздел «Реальные посетители» в отчёте.

## Как вводить команды из этой инструкции

- Команды в серых блоках копируйте **целиком** и вставляйте в Терминал (Cmd + V), затем **Enter**.
- **Обратные кавычки не вводите.** В тексте `вот так` — это только выделение. В Терминале обратные кавычки означают «выполни и подставь результат»: команда будет работать молча, а в конце выдаст ошибку.
- **Папка агента в командах — `~/Documents/site-speed-checker`.** Так она будет называться, если установить агента по разделу 1 (`~` — ваша домашняя папка, `Documents` — «Документы»). Если вы положили агента в другое место, замените этот путь в командах на свой.
- **Свой путь проще всего вставить из Finder:** наберите в Терминале `cd ` (с пробелом), перетащите папку агента из Finder в окно Терминала — путь подставится сам — и нажмите **Enter**.
- **Если в пути есть пробелы, возьмите его в двойные кавычки**, а `~` замените на `$HOME`: например, `cd "$HOME/Мои проекты/site-speed-checker"`.
- Большинство команд начинаются с `cd ~/Documents/site-speed-checker &&`: сначала переход в папку агента, затем сама команда. Поэтому неважно, в какой папке сейчас Терминал.

## 1. Подготовка (один раз на компьютере)

### 1.1. Проверить, что установлен Node.js

Откройте **Терминал** (Cmd + Пробел → «Терминал») и выполните:

```bash
node -v
```

Если в ответ напечаталась версия `v18` или новее (например, `v25.9.0`) — всё в порядке, переходите к 1.2.

> **Windows.** Агент работает и на Windows: команды `npm …` те же, запускайте их в Windows Terminal или PowerShell. Путь к папке пишется в формате Windows, например `cd "$HOME\Documents\site-speed-checker"`; команды `open` (открыть файл или папку) замените на `start`.

Если появилось `command not found` — установите Node.js одним из способов:
- скачайте установщик «LTS» с сайта https://nodejs.org и установите как обычную программу;
- или, если установлен Homebrew: `brew install node`.

После установки закройте и заново откройте Терминал и снова проверьте `node -v`.

### 1.2. Скачать агента

Агент лежит в открытом репозитории https://github.com/crabpipl/site-speed-checker — скачать его может любой, регистрация на GitHub не нужна. Положите агента в папку «Документы» под именем `site-speed-checker` — тогда все команды из инструкции сработают без изменений.

**Вариант А — через Git** (рекомендуется: потом обновления забираются одной командой, раздел 7):

```bash
cd ~/Documents && git clone https://github.com/crabpipl/site-speed-checker.git
```

Если на Mac появится окно с предложением установить «инструменты разработчика командной строки» — нажмите **Установить**, дождитесь окончания и выполните команду ещё раз. На Windows сначала установите Git с https://git-scm.com/download/win (все параметры по умолчанию).

**Вариант Б — архивом, без Git:** откройте https://github.com/crabpipl/site-speed-checker, нажмите зелёную кнопку **Code** → **Download ZIP**, распакуйте архив в «Документы» и переименуйте папку `site-speed-checker-main` в `site-speed-checker`. Обновления в этом варианте — так же: скачать архив заново (свои `pages.txt`, `settings.txt` и другие настройки перед этим сохраните).

Проверить, что всё на месте (должны появиться `README.md`, `check.js`, `pages.example.txt` и другие файлы):

```bash
ls ~/Documents/site-speed-checker
```

### 1.3. Установить зависимости агента

Установите зависимости (скачается Playwright и браузер Chromium, ~150 МБ, 1–3 минуты):

```bash
cd ~/Documents/site-speed-checker && npm install
```

Это делается **один раз**. Повторять нужно только если вы перенесли проект на другой компьютер, удалили папку `node_modules` или обновили версию Playwright в `package.json`.

### 1.4. Данные реальных посетителей (необязательно, один раз)

Агент может показывать рядом со своим замером, как страница работает у **настоящих посетителей** в Chrome. Эти данные Google собирает сам (Chrome UX Report, CrUX) и именно по ним оценивает Core Web Vitals при ранжировании. Без ключа агент работает как раньше, а в отчёте будет подсказка, что раздел не подключён.

Нужен бесплатный ключ Google API (платить не нужно, карта не требуется):

1. Откройте https://console.cloud.google.com и войдите в любой аккаунт Google.
2. Вверху нажмите выбор проекта → **New project** (Новый проект), назовите, например, `site-speed-checker` → **Create**.
3. Откройте https://console.cloud.google.com/apis/library/chromeuxreport.googleapis.com — это **Chrome UX Report API** — и нажмите **Enable** (Включить). Проверьте, что вверху выбран созданный проект.
4. Откройте https://console.cloud.google.com/apis/credentials → **Create credentials** → **API key**. Скопируйте ключ (длинная строка, начинается с `AIza`).
5. Рекомендуется ограничить ключ: в его настройках **API restrictions** → **Restrict key** → отметьте только **Chrome UX Report API** → **Save**.
6. Создайте в папке агента пустой файл **`crux-key.txt`** и откройте его:

```bash
touch ~/Documents/site-speed-checker/crux-key.txt && open -e ~/Documents/site-speed-checker/crux-key.txt
```

Вставьте ключ одной строкой, сохраните (Cmd + S) и закройте TextEdit.

Файл `crux-key.txt` не попадает в GitHub (он в `.gitignore`): у каждого пользователя агента свой ключ. Лимит Google — 150 запросов в минуту, агенту на одну страницу нужно 2–3 запроса, так что его хватает с запасом.

**Почему данных может не быть.** Google публикует статистику только для страниц и сайтов с заметным трафиком из Chrome. Если у страницы мало визитов, агент покажет данные по сайту в целом; если мало и у сайта — напишет, что данных нет.

## 2. Список страниц для проверки

Список хранится в файле **`pages.txt`** в папке агента. Это ваш личный файл: в репозиторий он не попадает и при обновлении агента не меняется. При первом запуске (например, `npm run pages`) агент сам создаёт его из образца `pages.example.txt` и подсказывает, где он лежит:

```
~/Documents/site-speed-checker/pages.txt
```

Откройте его любым текстовым редактором (TextEdit, VS Code) или из терминала:

```bash
open -e ~/Documents/site-speed-checker/pages.txt
```

**Правила:**

| Что нужно | Как сделать |
|---|---|
| Добавить страницу | Новая строка с полным адресом, начиная с `https://` |
| Удалить страницу | Удалить строку |
| Временно не проверять | Поставить `#` в начале строки |
| Комментарий / заголовок группы | Строка, начинающаяся с `#` |

Пустые строки игнорируются, повторяющиеся адреса проверяются один раз. Строки без `https://` агент пропустит и напишет предупреждение с номером строки.

**Заголовки и разделение по сайтам не нужны** — адреса можно добавлять просто списком, страницы разных сайтов можно смешивать в любом порядке. Агент сам определит сайт по адресу и сложит отчёты каждого сайта в свою папку (см. раздел 4). Строки с `#` можно использовать как подписи для себя — на проверку они не влияют.

Пример:

```
https://shop.example.com/cat/man/obuv/
https://store.example.com/smartfony/
https://shop.example.com/product/12345/
# https://shop.example.com/cat/kids/      ← эта страница сейчас не проверяется
```

Проверить, какие страницы попадут в замер и в какие папки сайтов (без запуска замера):

```bash
cd ~/Documents/site-speed-checker && npm run pages
```

### 2.1. Что нажимается при тесте отклика (`actions.txt`)

Агент **не нажимает все кнопки подряд**. Он определяет тип страницы и нажимает не больше одного элемента каждого вида из набора для этого типа — то, что чаще всего делает покупатель:

| Тип страницы | Что нажимается (если есть на странице) |
|---|---|
| Каталог | «Фильтры» (кнопка открытия панели фильтров), «Сортировка», «Показать ещё», меню, поиск |
| Карточка товара | выбор размера / варианта, «В корзину» (только кнопка самого товара, не в рекомендациях), стрелка галереи товара, меню, поиск |
| Другая страница | меню, стрелка галереи / слайдера, поиск |

- **Тип страницы** определяется по признакам: разметка товара, артикул в адресе, количество цен и карточек товаров на странице (карусели «Похожие товары» не учитываются), наличие фильтров и сортировки.
- **В поиск** вводятся первые слова заголовка страницы (H1) — например, «смартфоны» или «мужская обувь».
- Каждое действие выполняется с исходной страницы: после нажатия агент закрывает открывшиеся панели (Escape). Элемент, который виден только внутри другой панели (например, сортировка внутри мобильного фильтра), будет отмечен как скрытый.

**Точный список нажатий для сайта** задаётся в файле **`actions.txt`** в папке агента. Если сайт там не описан — работает автоматика выше. Пример:

```
[shop.example.com]
каталог  = Фильтр; Сортировка; Показать ещё
карточка = css: .product-sizes button; В корзину
поиск    = кроссовки
адреса каталога = /cat/
адреса карточки = /d/
```

| Строка | Что значит |
|---|---|
| `[сайт]` | начало настроек сайта (домен без `www.` и `https://`) |
| `каталог = …` / `карточка = …` / `другие = …` | что нажимать на страницах этого типа, по порядку, через `;` — **видимый текст кнопки** (как на сайте, регистр не важен) или CSS-селектор с приставкой `css:`. Задан список — нажимается ровно он |
| `поиск = слово` | что вводить в поиск; `поиск = нет` — не проверять поиск |
| `адреса каталога = …` / `адреса карточки = …` | часть адреса, по которой страница считается каталогом или карточкой — если автоматика ошибается |

В отчёте видно, какой тип страницы определён и откуда взяты нажатия (автоматически или из `actions.txt`); кнопка из `actions.txt`, которой нет на странице, отмечается красным. Ошибки в самом файле (неизвестный ключ, строка без сайта) агент выводит в Терминал при запуске.

### 2.2. Бюджеты скорости (`budgets.txt`)

**Бюджет** — это пороги, за которые страницы не должны выходить: например, «LCP не больше 2,5 с», «вес страницы не больше 4 МБ», «не больше 25 внешних сервисов». После каждой проверки агент сверяет с ними результат и сообщает:

- в начале отчёта — блок **«Бюджет скорости»**: какие страницы вышли за бюджет и по каким показателям. Красная плашка — нарушение **впервые** (в прошлой проверке показатель был в норме), жёлтая — **повторно**. Ниже — что **вернулось в бюджет**;
- в сводке по страницам — колонка «Бюджет»;
- в конце проверки в Терминале — строка **🔔 Вне бюджета** со списком страниц и новых нарушений;
- в папке отчёта — файл `budget.csv` со всеми нарушениями (для Excel).

Пороги хранятся в файле **`budgets.txt`** в папке агента. В нём уже записаны пороги по умолчанию — «хорошие» значения Google для Core Web Vitals и разумные пределы веса страницы. Открыть файл:

```bash
open -e ~/Documents/site-speed-checker/budgets.txt
```

Формат — строка «показатель = значение»:

```
LCP = 2,5 с
TBT (мобильный) = 600 мс
вес страницы = 4 МБ
внешних сервисов = 25
ошибок = 0

[shop.example.com]
LCP (мобильный) = 4 с
```

| Что | Как писать |
|---|---|
| Время | `2,5 с`, `2.5 с` или `800 мс` |
| Вес | `4 МБ` или `500 КБ` |
| CLS и количества | просто число: `0,1`, `25` |
| Порог только для одного разрешения | после названия в скобках: `(десктоп)` или `(мобильный)` |
| Свои пороги для сайта | секция `[имя сайта]` (без `www` и `https://`) — её строки заменяют общие |
| Не проверять показатель | закомментировать строку знаком `#` |

Показатели: `TTFB`, `FCP`, `LCP`, `TBT`, `CLS`, `полная загрузка`, `отклик` (INP из теста нажатий), `вес страницы`, `вес JS`, `вес картинок`, `запросов`, `внешних сервисов`, `ошибок` (ошибки загрузки ресурсов, повторившиеся минимум в двух прогонах), `DOM` (число элементов), `LCP посетителей`, `INP посетителей`, `CLS посетителей` (данные реальных посетителей, раздел 1.4).

**Совет.** Если сайт пока далёк от норм Google, всё будет красным, и новые проблемы потеряются среди старых. Тогда поставьте бюджет чуть хуже текущих значений сайта: так агент будет сигналить, когда станет **хуже, чем сейчас**. По мере улучшений бюджет можно ужесточать.

Ошибки в файле (неизвестный показатель, непонятное значение) агент выводит в Терминал при запуске. Если файла нет, бюджеты не проверяются.

### 2.3. Настройки агента (`settings.txt`)

Общие переключатели агента хранятся в файле **`settings.txt`** в папке агента. Как и `pages.txt`, это ваш личный файл: в репозиторий не попадает, при первой проверке создаётся из образца `settings.example.txt`. Открыть:

```bash
open -e ~/Documents/site-speed-checker/settings.txt
```

| Настройка | Что делает |
|---|---|
| `сводка для руководства = да` / `нет` | Создавать ли краткую сводку для руководства `summary.html` (раздел 4). По умолчанию в файле стоит `нет`: для повседневной проверки разработчиками она обычно не нужна |
| `задачи для трекера = да` / `нет` | Создавать ли задачи для трекера — `tasks.html` и `tasks.csv` (раздел 4). По умолчанию — `да` |
| `сравнение теста с продом = да` / `нет` | При проверке тестового контура (`npm run audit:test`) замерять ли те же пути на проде для сравнения (раздел 2.5). По умолчанию — `да` |
| `сравнение с конкурентами = да` / `нет` | Замерять ли страницы конкурентов из `competitors.txt` и показывать сравнение (раздел 2.4). По умолчанию — `нет` |
| `расписание = пн 03:00` | Когда запускать проверку по расписанию (раздел 3.1) |
| `проверка по расписанию = полная` / `быстрая` | Какую проверку запускать по расписанию. По умолчанию — `полная` |

Флаг при запуске важнее файла: добавьте к команде `--summary`, чтобы получить сводку один раз, не меняя файл (или `--no-summary`, чтобы разово её не создавать). Так же работают `--tasks` и `--no-tasks` для задач трекера и `--competitors` / `--no-competitors` для сравнения с конкурентами. Например:

```bash
cd ~/Documents/site-speed-checker && npm run audit -- --summary
```

Если файл удалить, при следующем запуске агент снова создаст его из образца `settings.example.txt`. Новые настройки, которые появляются при обновлении агента, смотрите в `settings.example.txt` и при желании переносите в свой `settings.txt`. Ошибки в файле агент выводит в Терминал при запуске.

### 2.4. Сравнение с конкурентами (`competitors.txt`)

Агент может замерить похожие страницы конкурентов в той же проверке и показать, кто быстрее. **По умолчанию сравнение выключено** — оно делает проверку дольше.

**1. Включите** в `settings.txt` (раздел 2.3):

```
сравнение с конкурентами = да
```

Или только для одного запуска, не меняя файл, — флаг `--competitors`:

```bash
cd ~/Documents/site-speed-checker && npm run audit -- --competitors
```

**2. Перечислите страницы** в файле **`competitors.txt`** в папке агента:

```bash
open -e ~/Documents/site-speed-checker/competitors.txt
```

Одна строка — одна группа похожих страниц: название, знак `=`, затем **сначала наша страница**, потом страницы конкурентов, через `;`:

```
Главная   = https://store.example.com/ ; https://competitor-a.example.com/ ; https://competitor-c.example.com/
Смартфоны = https://store.example.com/smartfony/ ; https://competitor-a.example.com/catalog/smartfony/ ; https://competitor-b.example.com/catalog/smartfony/
```

Правила:
- наша страница должна быть в `pages.txt` — её замер берётся из той же проверки; если её там нет, агент предупредит и пропустит группу;
- сравнивайте похожие страницы: главную с главной, каталог с каталогом, карточку товара с карточкой похожего товара;
- строки с `#` — комментарии; конкурентов в группе может быть сколько угодно, но каждый добавляет около 2 минут в каждом разрешении.

**Как замеряются конкуренты.** После своих страниц агент открывает страницы конкурентов столько же раз, в том же разрешении и с тем же замедлением сети и процессора — условия одинаковые, поэтому цифры можно сравнивать. Углублённые тесты (без внешних сервисов, повторный визит, отклик, неиспользуемый код, SEO) для конкурентов не делаются: нужны только цифры скорости, раскадровка и данные реальных посетителей (если подключён ключ, раздел 1.4).

**Что будет в отчёте** — раздел **«Сравнение с конкурентами»** в начале отчёта, по каждой группе и разрешению:
- **место по скорости** — по LCP, времени появления главного содержимого: например, «Мобильный: 3-е место из 3 — у нас 32 с, у лидера 3 с, в 10,7 раза дольше»;
- **таблица**: оценка, LCP, FCP, TTFB, TBT, CLS, полная загрузка, вес страницы, число запросов и внешних сервисов, реальные посетители; лучшее значение в каждой колонке отмечено ★, наша строка выделена;
- **кадры «что видит посетитель»** на каждом сайте через 0,5, 1, 2, 3, 5… секунд — сразу видно, у кого товары появляются раньше.

Те же цифры — в файле `competitors.csv` в папке каждого разрешения. Если включена сводка для руководства, в ней появляется блок «Мы и конкуренты» с местом по скорости.

### 2.5. Тестовый контур (`pages-test.txt`)

Тестовые сайты (стенды перед релизом) проверяются **отдельным списком и отдельной командой**, а не через `pages.txt`. Так:
- тестовый контур не попадает в обычную проверку и в проверку по расписанию прода;
- отчёты и история сравнений теста лежат отдельно — в папке тестового домена в `reports/`;
- выключаются проверки, которые для теста бессмысленны или дают ложные тревоги: SEO (тестовый сайт обычно закрыт от поисковиков — иначе это «критично» попало бы в рекомендации и бюджет), данные реальных посетителей (их у теста нет) и сравнение с конкурентами;
- прод-домен считается «своим»: файлы, которые тестовый сайт берёт с прод-CDN, не попадают во «внешние сервисы»;
- каждая тестовая страница **сравнивается с тем же путём на проде** — в той же проверке и в тех же условиях.

**1. Перечислите тестовые страницы** в файле `pages-test.txt` в папке агента:

```bash
open -e ~/Documents/site-speed-checker/pages-test.txt
```

Сначала строка в квадратных скобках: **тестовый домен = прод-домен**, под ней — адреса тестовых страниц:

```
[store.stage.company.local = store.example.com]
https://store.stage.company.local/
https://store.stage.company.local/smartfony/
https://store.stage.company.local/catalog/12345/
```

Для каждой страницы агент возьмёт тот же путь на прод-домене (`https://store.example.com/smartfony/` и т. д.). Порт тестового стенда, если он есть в адресе (`:8080`), к проду не переносится. Тестовых сайтов может быть несколько — каждый со своей строкой в скобках. Страница без такой строки проверяется без сравнения с продом.

**2. Запустите проверку тестового контура:**

```bash
cd ~/Documents/site-speed-checker && npm run audit:test
```

Это полная проверка обоих разрешений, как `npm run audit`. Дополнительные настройки работают так же: например, быстрая проверка — `npm run audit:test -- --quick`, без сравнения с продом — `npm run audit:test -- --no-prod`. Каждая прод-страница добавляет около 2 минут в каждом разрешении.

**Что будет в отчёте.** Заголовок с пометкой **«тестовый контур»** и в начале раздел **«Тест против прода»**: по каждой странице — показатели теста и прода рядом, разница (красным — заметно хуже прода, зелёным — заметно лучше, серым — в пределах разброса замеров), вердикт «медленнее прода» / «на уровне прода» / «быстрее прода» и кадры «что видит посетитель» на тесте и на проде в одни и те же моменты. В конце проверки в Терминале — строка **🧪 Тест медленнее прода** со списком страниц, если такие есть.

Учтите: тестовые серверы часто слабее прода и работают без CDN, поэтому небольшое отставание теста — нормально. Важнее, чтобы оно не росло от релиза к релизу: для этого есть сравнение с прошлой проверкой теста (раздел «Изменения с прошлой проверки») и бюджеты (раздел 2.2; для тестового домена можно задать свои пороги секцией `[тестовый домен]` в `budgets.txt`).

**Доступ.** Агент открывает тестовые страницы как обычный браузер: если стенд доступен только через VPN или из офисной сети, проверку нужно запускать с подключённым VPN или из этой сети.

## 3. Запуск проверки

Скопируйте нужную команду целиком — она сама перейдёт в папку агента и запустит проверку.

**Основной режим: десктоп, затем мобильный + общий отчёт**

```bash
cd ~/Documents/site-speed-checker && npm run audit
```

**Только десктоп**

```bash
cd ~/Documents/site-speed-checker && npm run audit:desktop
```

**Только мобильный** (Pixel 7, канал 1,6 Мбит/с, задержка 150 мс, процессор ×4 медленнее)

```bash
cd ~/Documents/site-speed-checker && npm run audit:mobile
```

**Показать список страниц из `pages.txt`** (без замера)

```bash
cd ~/Documents/site-speed-checker && npm run pages
```

**Если Терминал уже находится в папке проекта** (в приглашении видно `site-speed-checker %`, проверить можно командой `pwd`), достаточно коротких команд:

- полная проверка, десктоп и мобильный:
  ```bash
  npm run audit
  ```
- быстрая проверка, без теста внешних сервисов и замера неиспользуемого кода:
  ```bash
  npm run audit -- --quick
  ```
- только показать список страниц, без проверки:
  ```bash
  npm run pages
  ```

Никаких других предварительных действий перед запуском не нужно.

**Сколько ждать.** Страницы проверяются по одной (параллельные замеры искажают время). На каждую страницу в каждом разрешении: 3 обычных прогона, 2 прогона без внешних сервисов, по 1 прогону без каждого из 3 самых тяжёлых сервисов, повторный визит (прогрев + 2 замера), тест отклика на нажатия, 1 прогон для замера неиспользуемого кода и SEO-запросы. Это ≈ 7 минут на страницу в одном разрешении. Для 5 страниц `npm run audit` (оба разрешения) занимает около 1 ч 10 мин, для 30 страниц — около 7 часов. Не закрывайте Терминал и не давайте компьютеру уснуть до надписи «Общий отчёт: …».

**Быстрый режим** — без теста «без внешних сервисов», повторного визита, теста отклика на нажатия и замера неиспользуемого кода (≈ 2 минуты на страницу в одном разрешении):

```bash
cd ~/Documents/site-speed-checker && npm run audit -- --quick
```

**Что видно в Терминале во время проверки.** Внизу постоянно обновляется панель прогресса (раз в секунду):

```
████████░░░░░░░░░░░░  38%  Этап 1/2 · Десктоп · проверено 2 из 5 стр., в очереди 2 · осталось ≈ 14 мин (+ мобильный этап ≈ 16 мин)
⠹ Стр. 3: /cat/woman/odezhda/ · прогон 2 из 3 · 0:21 · готово 45%, ещё ≈ 2:40
```

- первая строка — общий прогресс этапа: сколько страниц проверено, сколько в очереди и сколько осталось времени (для `npm run audit` — плюс примерная длительность мобильного этапа);
- вторая строка — текущая страница: какой шаг идёт сейчас и сколько он длится, процент готовности страницы и сколько на неё ещё нужно;
- крутящийся значок и секундомер показывают, что агент работает, даже когда один шаг идёт долго (страница может грузиться до 45 секунд).

Время оценивается по фактической скорости уже выполненных шагов, поэтому после первых 1–2 прогонов оценка становится точнее. Над панелью выводятся результаты каждого прогона. В узком окне Терминала панель автоматически сокращается.

**Как понять, что проверка завершена.** В самом конце агент выводит итог между двумя линиями:

```
──────────────────────────────────────────────────────────────────────
✅ Проверка полностью завершена!
🔔 Вне бюджета: 3 из 10 замеров страниц, новых нарушений: 2
   • Мобильный: store.example.com/smartfony/ — вне бюджета 4; впервые: LCP 5.98 с > 2.50 с; и ещё CLS, Вес страницы, Внешних сервисов
   …
   Время проверки: 1 ч 27 мин
   Отчёт: …/reports/store.example.com/2026-10-14_11-21/all_report.html
   Задачи для трекера: …/reports/store.example.com/2026-10-14_11-21/tasks.html
──────────────────────────────────────────────────────────────────────
```

- **«✅ Проверка полностью завершена!»** (зелёным) — все страницы проверены во всех разрешениях, отчёт создан.
- **«⚠ Проверка завершена, но с ошибками»** (жёлтым) — часть страниц не открылась (сайт не ответил, страница не существует и т. п.). Ниже будет список таких страниц с причиной; отчёт по остальным страницам создан.
- **Итога нет** — значит, проверка не дошла до конца: её остановили (будет сообщение «Проверка остановлена») или она завершилась с ошибкой. В первом случае её можно продолжить (см. ниже).

### Пауза, остановка и продолжение

Во время проверки в окне Терминала работают клавиши:

| Клавиша | Что делает |
|---|---|
| **P** (или **З** в русской раскладке) | **Пауза.** Агент доделывает текущий шаг (одну загрузку страницы, обычно до 45 секунд) и ждёт. Пока шаг доделывается, на панели видно «⏸ пауза после этого шага», затем — «⏸ ПАУЗА». Повторное нажатие **P** — продолжить. Пауза не искажает замеры и не учитывается в оценке оставшегося времени |
| **Ctrl + C** | **Остановить проверку.** Результаты уже проверенных страниц сохраняются |

Не используйте **Ctrl + Z** для паузы: агент её не обрабатывает, а при обычной паузе терминала браузер продолжал бы загружать страницу, и замер был бы испорчен.

**Продолжение после остановки.** Агент сохраняет результат каждой страницы сразу после её проверки. Если проверку остановили (Ctrl + C), закрыли Терминал или ноутбук, пропал интернет — запустите **ту же команду** ещё раз. Агент покажет, что уже готово, и спросит:

```
Найдена незавершённая проверка этого списка страниц от 13.10.2026, 14:05:
  Десктоп: готово, 5 из 5
  Мобильный: проверено 2 из 5 стр.
Продолжить с места остановки? [Д/н] (н — начать заново):
```

- **Enter** или **Д** — продолжить: готовые страницы и этапы пропускаются, отчёт сохраняется в папку той, прерванной проверки (с её датой и временем);
- **Н** — начать заново.

Продолжить можно, только если список страниц в `pages.txt` и режим проверки (например, `--quick`) не менялись — иначе это уже другая проверка, и она начнётся с начала. Страница, на которой проверку остановили, проверяется заново целиком. Незавершённые проверки хранятся 14 дней.

Ответить на вопрос заранее можно параметром: `--resume` — продолжить без вопроса, `--fresh` — начать заново без вопроса:

```bash
cd ~/Documents/site-speed-checker && npm run audit -- --fresh
```

### 3.1. Проверка по расписанию

Агент может запускаться сам — например, каждый понедельник в 3 ночи. Так динамика копится без участия человека, а сравнение с прошлой проверкой и бюджеты сразу показывают, если что-то ухудшилось.

**1. Задайте время** в файле `settings.txt` (раздел 2.3) — уберите `#` в начале строки `расписание` и поставьте свои дни и время:

```
расписание = пн 03:00
проверка по расписанию = полная
```

| Как писать дни | Пример |
|---|---|
| Один день | `пн 03:00` (или `понедельник 03:00`) |
| Несколько дней | `пн, чт 03:00` |
| Каждый день | `ежедневно 02:30` |
| Будни / выходные | `будни 04:00`, `выходные 03:00` |

`полная` — обычная полная проверка обоих разрешений (около 14 минут на страницу), `быстрая` — без углублённых тестов (около 4 минут на страницу). Время — по часам этого компьютера.

**2. Включите расписание** — команда одна для всех систем:

```bash
cd ~/Documents/site-speed-checker && npm run schedule:on
```

Агент запишет задание в планировщик системы: на **macOS** — в launchd, на **Windows** — в Планировщик заданий (задача `SiteSpeedChecker`), на **Linux** — в cron текущего пользователя. После каждого изменения строк расписания в `settings.txt` выполните эту команду снова.

**Посмотреть**, включено ли расписание и чем закончился последний запуск:

```bash
cd ~/Documents/site-speed-checker && npm run schedule:status
```

**Выключить:**

```bash
cd ~/Documents/site-speed-checker && npm run schedule:off
```

**Запустить проверку так, как её запускает расписание, прямо сейчас** — чтобы убедиться, что всё работает:

```bash
cd ~/Documents/site-speed-checker && npm run schedule:run
```

**Что происходит при запуске по расписанию:**
- проверяются страницы из `pages.txt`, без вопросов (незавершённая прошлая проверка не продолжается, а начинается заново);
- всё, что агент обычно пишет в Терминал, сохраняется в журнал `reports/_schedule/<дата_время>.log` (хранятся последние 30);
- отчёты складываются как обычно (раздел 4), сравнение с прошлой проверкой и бюджеты работают;
- в конце — уведомление на рабочем столе с итогом: завершена ли проверка и что вышло за бюджет;
- если прошлая проверка по расписанию ещё идёт, новая не начинается;
- пока идёт проверка, компьютер не уходит в сон (на macOS и Linux).

**Важно для каждой системы:**

| Система | Что учесть |
|---|---|
| macOS | Компьютер должен быть включён; если он спал во время запуска, проверка начнётся после пробуждения. Если в `reports/_schedule/launchd.log` есть `Operation not permitted`, macOS не даёт фоновой программе доступ к папке «Документы»: «Системные настройки» → «Конфиденциальность и безопасность» → «Полный доступ к диску» → «+» → добавьте `node` (путь покажет команда `which node`; в окне выбора нажмите Cmd + Shift + G и вставьте его), или перенесите папку агента из «Документов» |
| Windows | Компьютер должен быть включён и пользователь — вошедшим в систему (задача запускается от его имени). Если компьютер был в спящем режиме, пропущенный запуск не выполнится — измените время или настройте задачу `SiteSpeedChecker` в «Планировщике заданий» (вкладка «Условия» → «Пробуждать компьютер для выполнения задачи»; вкладка «Параметры» → «Немедленно запускать задачу, если плановый запуск пропущен») |
| Linux | Компьютер или сервер должен быть включён. Нужны системные пакеты — см. ниже. Уведомление показывается, только если есть рабочий стол; итог всегда есть в `npm run schedule:status` и в журнале |

**Linux: что установить один раз.** На macOS и Windows всё нужное уже встроено в систему. На Linux, особенно на чистой или серверной установке, может понадобиться доустановить:

1. **Системные библиотеки для браузера** — обязательно (без них Chromium не запустится вообще, не только по расписанию). В папке агента:

   ```bash
   sudo npx playwright install-deps chromium
   ```

   Эта команда работает на Ubuntu и Debian (и основанных на них системах) — на них Playwright и рассчитан. На Fedora, Arch и других дистрибутивах она не сработает: Playwright там официально не поддерживается, нужные библиотеки придётся ставить вручную по сообщению об ошибке при первом запуске (`npm run audit:desktop`). Для проверки по расписанию на сервере удобнее всего Ubuntu.

2. **cron** — планировщик, в который агент записывает расписание. На Ubuntu и Debian обычно уже есть; в минимальных установках, на Fedora и Arch его может не быть — тогда `npm run schedule:on` напишет, что программа `crontab` не найдена. Установка и включение службы:

   | Дистрибутив | Установить | Включить и запустить службу |
   |---|---|---|
   | Ubuntu, Debian, Linux Mint | `sudo apt install cron` | `sudo systemctl enable --now cron` |
   | Fedora, CentOS, RHEL, Rocky, AlmaLinux | `sudo dnf install cronie` | `sudo systemctl enable --now crond` |
   | Arch, Manjaro | `sudo pacman -S cronie` | `sudo systemctl enable --now cronie` |
   | openSUSE | `sudo zypper install cronie` | `sudo systemctl enable --now cron` |

   Проверить, что служба работает: `systemctl status cron` (на Fedora/CentOS — `crond`, на Arch — `cronie`) — в ответе должно быть `active (running)`.

3. **По желанию — уведомление на рабочем столе** (программа `notify-send`):

   | Дистрибутив | Команда |
   |---|---|
   | Ubuntu, Debian, Linux Mint | `sudo apt install libnotify-bin` |
   | Fedora, CentOS, RHEL | `sudo dnf install libnotify` |
   | Arch, Manjaro | `sudo pacman -S libnotify` |
   | openSUSE | `sudo zypper install libnotify-tools` |

   На сервере без рабочего стола ставить не нужно — уведомление там всё равно некуда показать.

Защиту от сна на время проверки агент включает через `systemd-inhibit` — он есть во всех системах с systemd; если его нет, проверка всё равно запустится.

### 3.2. Тест оформления заказа (`checkout.txt`)

Отдельный тест: агент входит в личный кабинет по коду из SMS или письма и **оформляет настоящий заказ**: карточки товаров → корзина (товары, которые лежали в ней до теста, удаляются) → оформление → способ получения → способ оплаты → «Оформить заказ». Каждый шаг замеряется: сколько ждёт покупатель после нажатия, какие запросы к серверу самые долгие, есть ли ошибки, как быстро откликаются кнопки, что видно на экране.

> ⚠ **Каждый запуск создаёт настоящий заказ.** После теста отмените его в личном кабинете или попросите оператора. Проверить сценарий без заказа можно режимом `--check` (см. ниже).

Этот тест запускается **только вручную**: нужен код, который приходит вам. В проверку по расписанию он не входит.

**1. Заполните настройки** в файле `checkout.txt` в папке агента. При первом запуске файл создаётся из образца `checkout.example.txt`, в нём описаны все строки. Открыть его:

```bash
open -e ~/Documents/site-speed-checker/checkout.txt
```

Минимальный пример:

```
[shop.example.com]
товар      = https://shop.example.com/catalog/cable-usb-c/; https://shop.example.com/catalog/charger/
разрешение = мобильный
вход       = спрашивать
адрес корзины = https://shop.example.com/cart/
получение  = Самовывоз
показать магазины   = Показать списком
магазин    = ул. Примерная, 1
подтвердить магазин = Забрать здесь
оплата     = При получении
```

- **товар** — недорогой товар, который точно есть в наличии. Чтобы проверить корзину с несколькими товарами, перечислите адреса через `;` (`товар = адрес1; адрес2`) или напишите несколько строк `товар = …`. Агент откроет каждую карточку, **обновит страницу** и уже с обновлённой добавит товар в корзину: так замер идёт с прогретым кэшем, как у вернувшегося покупателя (впервые на сайт заходят редко). Первый заход тоже есть в отчёте — серым, со сравнением «первый заход → с прогретым кэшем». Выключить обновление: `обновлять карточку = нет`.
- **разрешение** — `мобильный` (по умолчанию) или `десктоп`. Один запуск — одно разрешение и один заказ.
- **вход** — `телефон`, `почта` или `спрашивать` (агент спросит при запуске).
- **телефон** или **почта** — можно указать сразу, тогда агент не спрашивает их в Терминале. Телефон пишется 10 цифрами без кода страны: `телефон = 9001234567`. Если указано только одно из двух, вход идёт этим способом.
- **получение**, **магазин**, **оплата** — пишите **текстом, как на кнопках сайта**. Их можно менять перед каждым тестом. Агент находит на странице кнопку или карточку с этим текстом и нажимает её. Хватит начала надписи (`получение = Курьерская доставка` подойдёт для «Курьерская доставка до двери»), регистр не важен; цену и дату («499 руб.», «завтра») не пишите — они меняются. Несколько вариантов — через `;`, нажимается первый найденный. Не знаете точный текст — уберите строку и запустите проверку `--check`: на этом шаге агент покажет варианты со страницы готовыми строками.
- **Корзина аккаунта очищается перед тестом** (служебный шаг «Очистка корзины перед тестом», в итог не входит) — в том числе от товаров, оставшихся с прошлых тестов: иначе кнопка на карточке ведёт в корзину, а не добавляет товар. Решение «корзина пуста» агент принимает только после того, как страница корзины загрузила данные (некоторые сайты сначала показывают заготовку «Корзина пуста»). Товары в блоках «Избранное», рекомендаций и каруселей не трогаются. Удалённые перечисляются в Терминале и в отчёте. Если удалять ничего нельзя, напишите `удалять другие товары = нет` — тогда тест остановится, если корзина не пуста (для этой проверки нужен `адрес корзины`). Если кнопка всё же открыла корзину вместо добавления, шаг помечается «не в счёт» и не входит в итог, рекомендации и сравнение.
- Если на сайте другие надписи на кнопках (вход, «В корзину», «Оформить»), их можно указать — список строк есть в `checkout.example.txt`. Вместо текста можно указать CSS-селектор с приставкой `css:`.
- Для тестового стенда добавьте отдельную секцию с его доменом.

Код в файл писать не нужно: агент спрашивает его в Терминале при каждом запуске. Телефон или почту — по желанию (см. выше), иначе агент тоже спросит их в Терминале.

**Как агент справляется с разными сайтами.** Тексты кнопок у магазинов разные, поэтому агент не полагается только на `checkout.txt`:
- **Всплывающие окна** — «Ваш регион — Москва? Да, верно», согласие на cookies («Принять», «Хорошо»), промо-окна со скидками и подписками — агент закрывает сам перед каждым шагом. Если нужную кнопку перекрывает другое окно, оно закрывается перед нажатием. Окна с полями ввода (вход, выбор магазина, адрес) агент не трогает. Время на закрытие окон в замер шага не входит; список закрытых окон — в отчёте.
- **Кнопки** ищутся сначала по вашим строкам из `checkout.txt`, затем по типовым текстам («Войти», «В корзину», «Перейти к оформлению» и др.), затем как **иконки** — по адресу ссылки (`/login`, `/profile`, `/order/cart`), подписи, классу и картинке. Кнопки, уводящие с пути оформления («Продолжить покупки», «В каталог», «Быстрый заказ»), при неточном совпадении текста не нажимаются. Кнопки «В корзину» / «Купить» в блоках рекомендаций («С этим товаром покупают», карусели других товаров) агент не нажимает — только кнопку самого товара.
- **Адрес корзины**, если он не указан, агент находит по ссылкам на сайте.
- **Время шага с нажатием** считается от момента нажатия: поиск кнопки агентом в замер не входит.
- **Размер, цвет, вариант товара** агент выбирает сам — отдельным шагом «Выбор размера / варианта» перед «В корзину»: если вариант уже выбран на сайте, он остаётся, иначе берётся первый доступный. Если сайт открывает панель «Выберите размер» только после нажатия «В корзину», агент выбирает размер в ней и нажимает «В корзину» ещё раз. Нужный вариант можно задать строкой `вариант = 42` (или `вариант = M; Чёрный`), отключить выбор — `вариант = нет`. Выбранный вариант виден в отчёте рядом с товаром.
- **Вход в меню.** Если на смартфоне кнопки или иконки входа нет на экране, агент открывает меню (☰) и ищет вход там.
- **Если кнопка не найдена**, в Терминале и в отчёте появляется список похожих элементов на этой странице — готовыми строками, которые можно вписать в `checkout.txt`, например `к оформлению = css: a[href="/order/"]`.

**Подключение нового сайта:** впишите в `checkout.txt` секцию с одной строкой `товар = …` и запустите проверку сценария `--check`. Агент пройдёт сколько сможет и на первом же непонятном шаге подскажет варианты. Впишите подходящую строку, повторите — обычно хватает 2–3 запусков. Чтобы подобрать «получение» и «оплата», их можно сначала не указывать: на этих шагах агент покажет варианты со страницы.

**Запись сценария — самый быстрый способ подключить сайт.** Пройдите оформление один раз сами в открытом окне браузера, а агент запомнит, какие кнопки вы нажимали:

```bash
cd ~/Documents/site-speed-checker && npm run audit:checkout -- --record --site=shop.example.com
```

1. Откроется окно браузера с сайтом, а в Терминале — подсказка к первому шагу. Шаги идут по порядку оформления: вход (можно пропустить), карточка товара, размер или цвет, «В корзину», переход в корзину, «К оформлению», способ получения, магазин, способ оплаты, «Оформить заказ».
2. На каждом шаге нажмите нужную кнопку на сайте и затем **Enter в Терминале**. Агент пишет, что записал. Ошиблись — введите `у` (удалить последнее нажатие); шага на сайте нет — `п` (пропустить).
3. Окна региона, cookies и промо закрывайте как обычно: такие нажатия не записываются, при тесте агент закрывает эти окна сам. То, что вы вводите в поля (телефон, код, адрес), тоже не записывается.
4. **На последнем шаге нажатие «Оформить заказ» перехватывается**: агент запоминает кнопку, но до сайта нажатие не доходит, отправка данных на сайт в этот момент тоже отменяется — заказ не создаётся.
5. Агент показывает готовую секцию и спрашивает, сохранить ли её в `checkout.txt`. Если секция сайта уже есть, она заменяется, а строки, которых запись не касается (`телефон`, `вход`, `основа` и др.), остаются. Прежний файл сохраняется рядом как `checkout.txt.bak`.

После записи проверьте сценарий режимом `--check` — агент подскажет команду. Записанные кнопки можно поправить в `checkout.txt` вручную, как обычно. Записывается разрешение из `--mobile` / `--desktop` (или строки `разрешение` в файле, по умолчанию мобильное): кнопки на смартфоне и компьютере бывают разными.

**Ограничения:** сайты, закрытые защитой от ботов (страница «Проверка браузера», DDoS-Guard, капча), автоматически не проходятся — тест остановится на главной странице с объяснением. В режиме `--check` агент заходит гостем; если сайт перед выбором доставки требует заполнить данные покупателя, проверка остановится на этой форме — полный тест со входом пройдёт её как обычно.

**Способ получения: самовывоз или курьер.** Тест оформляет заказ одним способом получения — тем, что указан в секции сайта в `checkout.txt`. Какой указан, такой и проверяется. Курьер выбирается строкой `адрес доставки`: если она есть — доставка курьером, если нет — самовывоз.

Пример настройки **самовывоза**:

```
[shop.example.com]
товар     = https://shop.example.com/catalog/item/
получение = Забрать в магазине
магазин   = ул. Примерная, 1
оплата    = При получении
```

Пример настройки **доставки курьером**:

```
[shop.example.com]
товар          = https://shop.example.com/catalog/item/
получение      = Курьерская доставка
адрес доставки = Москва, ул. Примерная, 1
квартира       = 1
оплата         = При получении
```

`shop.example.com` — условное имя, вместо него домен вашего сайта. В `получение`, `магазин`, `оплата` — текст кнопок, как на сайте. Запуск в обоих случаях одинаковый:

```bash
cd ~/Documents/site-speed-checker && npm run audit:checkout -- --site=shop.example.com
```

Дополнительные строки для курьера (необязательные):

| Строка | Что делает |
|---|---|
| `подъезд`, `этаж`, `домофон`, `комментарий курьеру` | заполняются, если поле на сайте пустое |
| `получатель` | имя получателя, если сайт не подставил его сам |
| `телефон получателя` | по умолчанию — телефон для входа |
| `дата доставки` | `завтра`, `23 октября`, `пт`; по умолчанию — первая доступная |
| `интервал` | `10:00 - 18:00`; по умолчанию — первый доступный |
| `подтвердить адрес` | кнопка в окне адреса; по умолчанию агент ищет «Сохранить», «Готово», «Продолжить» |

Адрес агент вводит по буквам и выбирает подсказку сайта, где совпадают улица и дом. В отчёте курьерского теста есть шаги «Адрес доставки — подсказки», «Адрес доставки — расчёт доставки», «Дата и интервал доставки». Если в секции есть и `адрес доставки`, и `магазин`, проверяется курьер — агент предупредит об этом при запуске.

**Несколько сайтов одной платформы.** Чтобы не переписывать одинаковые строки, в `checkout.txt` есть:
- секция `[все сайты]` — её строки действуют на все сайты (например, `телефон`, `разрешение`, `вход`);
- строка `основа = другой-сайт` в секции сайта — агент берёт все настройки другого сайта из этого файла, а в секции пишутся только отличия (обычно `товар`, `магазин`, иногда `вариант`).

Порядок применения: `[все сайты]` → `основа` → строки самого сайта (последние важнее). Адреса — `товар`, `адрес корзины`, `адрес профиля` — у каждого сайта свои и из основы не берутся. При запуске агент пишет в Терминале, какие настройки взяты из других секций. Пример:

```
[все сайты]
разрешение = мобильный

[shop.example.com]
товар     = https://shop.example.com/catalog/item/
получение = Забрать в магазине
оплата    = При получении

[store.example.com]
основа = shop.example.com
товар  = https://store.example.com/d/item/
```

**2. Проверьте сценарий без входа и без заказа** — после первой настройки и после изменений на сайте:

```bash
cd ~/Documents/site-speed-checker && npm run audit:checkout -- --check
```

Агент проходит все шаги гостем. Он проверяет, что форма входа открывается, и нажимает всё до кнопки «Оформить заказ», но саму её не нажимает. Если какой-то кнопки нет, в Терминале будет написано, на каком шаге и что поправить в `checkout.txt`.

**3. Проверьте со входом, но без заказа** — агент входит по коду и проходит все шаги до кнопки «Оформить заказ», но саму её не нажимает:

```bash
cd ~/Documents/site-speed-checker && npm run audit:checkout -- --site=shop.example.com --no-order
```

`shop.example.com` — имя секции сайта из `checkout.txt`. Добавленные товары останутся в корзине вашего аккаунта.

**4. Запустите тест с заказом** — та же команда без `--no-order`:

```bash
cd ~/Documents/site-speed-checker && npm run audit:checkout -- --site=shop.example.com
```

Откроется окно браузера, за тестом можно следить. Дальше:

1. Агент спрашивает телефон или почту — введите и нажмите Enter (если они указаны в `checkout.txt`, агент просто покажет, что взял оттуда). Код подтверждения потом вводится скрыто (вместо цифр — точки).
2. Агент открывает форму входа, вводит телефон или почту и нажимает «Получить код».
3. В Терминале появляется **«Код подтверждения»**. Введите код и нажмите Enter. На тестовом стенде возьмите код из базы. Код может прийти в SMS, push-уведомлением в приложении сайта, письмом или звонком (тогда код — последние цифры номера, с которого звонят). Другой способ можно выбрать прямо в окне браузера, например «Запросить звонок» или «Отправить код на e-mail», и затем ввести код в Терминале. Если код не пришёл, нажмите Enter без кода — агент отправит его ещё раз. Неверный код можно ввести заново (до трёх попыток).
4. Агент проходит оформление и пишет номер заказа: **«✓ Заказ № … оформлен. Не забудьте отменить его.»**
5. Агент **выходит из аккаунта, удаляет cookies и закрывает браузер**. В следующем тесте старого входа не будет.

Остановить тест в любой момент — **Ctrl + C**: агент выйдет из аккаунта и закроет браузер. Если сайт покажет капчу, пройдите её сами в окне браузера.

Дополнительные настройки запуска:

| Настройка | Что делает |
|---|---|
| `--check` | Проверка сценария гостем: без входа и без заказа |
| `--record` | Запись сценария: вы проходите оформление сами, агент запоминает кнопки и сохраняет секцию сайта в `checkout.txt` (заказ не создаётся) |
| `--no-order` | Вход по коду и все шаги, но без нажатия «Оформить заказ» (товар останется в корзине аккаунта) |
| `--rebuild=<папка отчёта>` | Пересобрать `checkout_report.html` и задачи по сохранённым данным текущей версией агента (например, после обновления) |
| `--desktop` / `--mobile` | Разрешение на этот запуск (вместо строки `разрешение` в файле) |
| `--site=shop.example.com` | Какой сайт проверить, если в `checkout.txt` их несколько (иначе агент спросит) |
| `--headless` | Без окна браузера |

Например, тест без заказа на компьютерной версии:

```bash
cd ~/Documents/site-speed-checker && npm run audit:checkout -- --no-order --desktop
```

**Онлайн-оплата.** Если в `оплата` указана онлайн-оплата картой, агент доходит до формы банка, замеряет её загрузку и останавливается. **Данные карты он не вводит** — заказ останется неоплаченным.

**Личные данные.** Телефон, почта, код и имя не попадают в тексты отчёта и журнал (телефон или почта хранятся только в вашем `checkout.txt`, если вы их туда вписали). В адресах запросов они заменены на `•••`. Ни в окне браузера, ни на кадрах отчёта ничего не размывается: строка поиска, поле телефона или почты, введённый код, имя и адрес на странице видны как есть. Поэтому перед пересылкой отчёта помните: на кадрах виден ваш номер или почта и другие данные заказа — пролистайте кадры.

**Результат** — в папке `reports/<сайт>/<дата_время>/checkout/`:
- `checkout_report.html` — отчёт: итог (заказ оформлен / где остановился), время «от карточки товара до заказа», **таблица шагов** с двумя временами — **«контент готов»** (покупатель уже видит страницу и может действовать; по нему считаются итог, сравнение и рекомендации) и **«полная загрузка»** (до события load и последних ответов внешних сервисов; если она намного дольше, рекомендация называет сервисы, которые её держат — например, зависший счётчик или пиксель), отклик кнопок, самые долгие запросы, ошибки, рекомендации (кому: бэкенд, фронтенд, маркетинг) и кадры экрана по каждому шагу. ▲/▼ — сравнение с прошлым тестом этого сайта на том же разрешении. Нажмите на адрес запроса, чтобы скопировать его полностью.
- `tasks.html` — **задачи для разработки** по найденным проблемам: одна карточка — одна задача (медленный запрос к серверу, медленные свои файлы, долгие задачи JavaScript, отклик кнопок, внешний сервис). В карточке: приоритет, исполнитель (бэкенд, фронтенд, маркетинг), где проблема (шаги и запросы с цифрами), что сделать по пунктам и «готово, когда» — с командой повторного теста. Кнопки «Копировать» переносят задачу в трекер; фильтры — по приоритету и исполнителю.
- `tasks.csv` — те же задачи таблицей для Excel.

**Как агент делает выводы.** Для каждого запроса записываются ожидание ответа (время до первого байта: работа сервера плюс задержка сети) и размер ответа. Если запрос долгий из‑за ожидания — задача бэкенду «ускорить ответ сервера»; если из‑за скачивания — «уменьшить ответ» или «уменьшить файл». Запросы, которые отменила сама страница (`ERR_ABORTED`, обычно отправка статистики при переходе), и запросы без ответа к концу шага ошибками не считаются. Все времена — при условиях профиля (для смартфона: сеть 1,6 Мбит/с, задержка 150 мс, процессор замедлен в 4 раза); они указаны в отчёте и в задачах. Сравнение ▲/▼ — только с тестом того же вида (гостем — с гостем, со входом — со входом).
- `data.json` — те же данные для пересборки.

Учтите: один тест — один заказ, поэтому прогон один, а не медиана нескольких. Отдельные шаги могут «прыгать» от запуска к запуску — сравнивайте несколько тестов в динамике.

## 4. Где искать результаты

Отчёты складываются **по сайтам**: у каждого сайта своя папка (домен без `www.`), внутри — папка на каждый запуск с датой и временем начала:

```
site-speed-checker/reports/
  shop.example.com/
    2026-10-12_14-09/
      all_report.html             ← отчёт: сравнение десктоп / мобильный + вкладки с полной детализацией
      summary.html                ← краткая сводка для руководства (если включена, раздел 2.3)
      tasks.html                  ← задачи для трекера: карточки с кнопками «Копировать» (если включены, раздел 2.3)
      tasks.csv                   ← те же задачи таблицей для Excel
      desktop/
        pages.csv                 ← метрики по страницам (для Excel)
        resources.csv             ← все запросы всех страниц
        services.csv              ← внешние сервисы и рекомендации
        budget.csv                ← что вышло за бюджет (раздел 2.2)
        competitors.csv           ← сравнение с конкурентами (если включено, раздел 2.4)
        data.json                 ← данные замера (из них собирается отчёт и сравнение с прошлой проверкой)
      mobile/
        … те же файлы …
    2026-10-14_10-30/
      …
  store.example.com/
    2026-10-13_11-00/
      …
```

При полной проверке (`npm run audit`) создаётся **один HTML-отчёт** — `all_report.html`. В нём есть всё: сравнение разрешений, общий итог по внешним сервисам и две вкладки «Десктоп» и «Мобильный» с полной детализацией. При проверке одного разрешения (`npm run audit:desktop` или `audit:mobile`) отчёт этого разрешения лежит в его папке: `desktop/desktop_report.html` или `mobile/mobile_report.html`.

Служебная папка `reports/.resume/` хранит сохранения незавершённых проверок (см. «Пауза, остановка и продолжение»); после успешного окончания проверки сохранение удаляется само.

Если в `pages.txt` страницы нескольких сайтов, проверка всё равно запускается одной командой — каждый сайт получит свою папку и свой отдельный отчёт (сводка, внешние сервисы, рекомендации — только по его страницам).

Открыть папку с отчётами в Finder:

```bash
open ~/Documents/site-speed-checker/reports
```

Отчёт `.html` открывается двойным щелчком в любом браузере.

**Сравнение с прошлой проверкой** делается автоматически: агент находит в папке **этого сайта** предыдущий запуск того же разрешения (проверки других сайтов между ними не мешают) и показывает изменения по совпадающим страницам (▲ хуже / ▼ лучше в сводке и отдельный раздел «Изменения с прошлой проверки»). Учитываются только изменения больше обычного разброса замеров. Чтобы сравнение было честным, проверяйте один и тот же набор страниц в одном режиме (обычный или `--quick`).

### Задачи для трекера (`tasks.html`)

Если задачи включены (по умолчанию да, раздел 2.3), рядом с отчётом агент кладёт **`tasks.html`** — все рекомендации проверки, собранные в задачи, чтобы перенести их в трекер вручную. Одинаковая проблема на разных страницах и в обоих разрешениях — **одна задача** со списком страниц. Задачи отсортированы по приоритету, затем по числу страниц.

Каждая задача — отдельная карточка:
- **заголовок** — что сделать, коротко: например, «Ускорить ответ сервера: кэширование HTML»;
- **приоритет** (Высокий / Средний / Низкий — самый высокий из всех страниц), **исполнитель** (Фронтенд, Бэкенд / администраторы, Маркетинг + фронтенд, Фронтенд / контент или SEO-специалист), **на скольких страницах** и в каких разрешениях, **выигрыш (измерен)** — только если он измерен в этой проверке (тест без внешних сервисов: «LCP быстрее на 2,3 с»), и **сейчас** — сколько проблема занимает в замере («TTFB 1,11 с», «эта часть LCP — 3,4 с», «оценка экономии 1,2 МБ»). Обещаний «станет быстрее на …» без замера агент не даёт;
- описание: почему это важно и как исправить; раскрывающиеся списки «Где и с какими значениями» (по каждой странице и разрешению) и «Подробности» (конкретные файлы, сервисы, элементы).

**Как переносить в трекер:** откройте `tasks.html` двойным щелчком, создайте задачу в трекере и нажмите в карточке **«Копировать заголовок»**, затем **«Копировать описание»** — в описание попадают приоритет, исполнитель, выигрыш, список страниц со значениями и подробности. Поставьте галочку **«перенесено»** — карточка станет бледной, а фильтр «Не перенесённые» покажет, что осталось. Отметки запоминаются в этом браузере на этом компьютере.

Вверху страницы — фильтры по приоритету и исполнителю: например, «Бэкенд / администраторы» покажет только задачи для бэкенда. Страницу можно распечатать (Cmd + P) — тогда все списки раскроются.

Те же задачи таблицей — в **`tasks.csv`** (открывается в Excel или Numbers двойным щелчком): колонки «Задача», «Описание», «Приоритет», «Исполнитель», «Страниц», «Разрешения», «Выигрыш (измерен)», «Сейчас», «Страницы».

### Краткая сводка для руководства (`summary.html`)

Если сводка включена (`сводка для руководства = да` в `settings.txt` или флаг `--summary`, раздел 2.3), рядом с полным отчётом агент кладёт **`summary.html`** — одностраничную сводку для руководителя, без технических терминов. Если проверялось одно разрешение, сводка лежит в его папке (`desktop/` или `mobile/`). В сводке:

- **оценка** («Хорошо», «Требует улучшения» или «Плохо») и одна фраза о том, через сколько секунд посетитель видит главное содержимое страницы. Оценка ставится по смартфонам: Google ранжирует сайт по мобильной версии;
- чем это грозит: по исследованию Google, насколько выше вероятность, что посетитель уйдёт, не дождавшись; проходит ли сайт оценку скорости Google по реальным посетителям (если подключён ключ, раздел 1.4);
- **ключевые цифры**: время до главного содержимого, повторный заход, число страниц вне норм из `budgets.txt`;
- **3–5 главных проблем**: что видит покупатель, сколько секунд можно выиграть, на скольких страницах проблема и кто её решает (маркетинг, фронтенд, бэкенд, SEO);
- **что изменилось** с прошлой проверки;
- короткая таблица страниц со временем до главного содержимого.

Открыть сводку последнего запуска — так же, как полный отчёт, только с именем `summary.html`. Распечатать или сохранить в PDF — **Cmd + P** → «Сохранить как PDF».

### Что внутри отчёта по каждой странице

| Раздел | Для кого и зачем |
|---|---|
| Тест против прода (в начале отчёта тестового контура) | Разработчики, тестировщики: не стала ли страница на тесте медленнее прода перед релизом |
| Сравнение с конкурентами (в начале отчёта, если включено) | Руководитель, маркетинг: место по скорости среди конкурентов, таблица показателей и кадры «что видит посетитель» на каждом сайте |
| Бюджет скорости (в начале отчёта) | Все: какие страницы вышли за пороги `budgets.txt`, впервые или повторно, и что вернулось в норму |
| Итоги и рекомендации | Список задач по приоритету — с чего начинать |
| Раскадровка загрузки | Все, особенно руководитель и дизайнер: что видит посетитель на экране во время загрузки — сколько смотрит на пустой экран, когда появляются товары, что сдвигается. Кадр с первым контентом (FCP) выделен синей рамкой, с главным элементом (LCP) — зелёной, сдвиги вёрстки подписаны красным. Вторая лента — повторный визит с прогретым кэшем и разница в секундах: насколько быстрее страница у вернувшегося покупателя (в быстром режиме `--quick` повторного визита нет — только первая лента) |
| Реальные посетители (Chrome UX Report) | Все: пройдены ли Core Web Vitals у настоящих посетителей (по этим данным ранжирует Google), доля хороших и плохих визитов, сравнение с замером агента, динамика за полгода и разбор LCP у посетителей |
| Сколько стоят внешние сервисы | Маркетинг/руководитель: сколько секунд дают внешние скрипты и какие именно. Если без внешних сервисов главным элементом страницы (LCP) становится другой — например, исчезает баннер внешнего сервиса, — LCP в этом сценарии не сравнивается, и отчёт об этом пишет |
| Отклик на действия (INP) | Фронтенд/маркетинг: как быстро страница реагирует на нажатия и чьи скрипты (свои или внешних сервисов) её при этом тормозят; какие всплывающие окна мешают нажимать |
| Повторный визит (прогретый кэш) | Все: насколько быстрее страница у вернувшегося покупателя; фронтенд/админы — какие свои файлы зря скачиваются заново и что поправить в `Cache-Control` |
| Разбор LCP | Разработчики: что чинить — сервер, позднюю загрузку картинки, её вес или отрисовку |
| Ответ сервера на запрос HTML | Бэкенд/админы: генерация HTML, TLS, кэширование |
| Таймлайн, ответы не 200, долгие 200, внешние сервисы, CPU | Детализация по каждому запросу. В таблицах запросов колонка «Из них ожидание ответа» — сколько ждали сервер; остальное время — скачивание: если оно большое, причина не в сервере, а в весе файла и общей очереди канала. Ссылки в таймлайне длинные и обрезаны — нажмите на название запроса слева, и полный адрес скопируется (внизу экрана появится «✓ Скопировано» с адресом целиком) |
| Неиспользуемый код | Фронтенд: какие бандлы раздуты |
| Картинки, шрифты, DOM | Фронтенд/контент: конкретные файлы и экономия |
| Источники сдвигов вёрстки | Фронтенд: какие элементы прыгают |
| SEO: что видят поисковые роботы | SEO-специалист: HTML без JS, ответ роботам, теги, robots.txt |

Пересобрать общий отчёт из сохранённых данных без нового замера (например, после обновления агента). Замеры при этом не меняются, а выводы, рекомендации и задачи пересчитываются по ним заново — исправления агента попадают и в старые отчёты. Замените путь `shop.example.com/2026-10-12_14-09` на нужный сайт и запуск:

```bash
cd ~/Documents/site-speed-checker && R=reports/shop.example.com/2026-10-12_14-09 && node combine.js $R/desktop $R/mobile
```

Если нужен **отдельный отчёт одного разрешения** (например, отправить мобильный разработчику мобильной версии), его можно собрать из тех же данных — появится `mobile/mobile_report.html`:

```bash
cd ~/Documents/site-speed-checker && node render.js reports/shop.example.com/2026-10-12_14-09/mobile
```

## 5. Частые проблемы

| Сообщение | Причина и решение |
|---|---|
| Тест оформления: «на странице нет варианта …» или «агент не нашёл, что выбрать» | Укажите размер или цвет в `вариант = …` точно как на сайте (список вариантов — в сообщении); для товара без вариантов — `вариант = нет` |
| Тест оформления: «сайт показал страницу защиты от ботов» | Сайт закрыт защитой (DDoS-Guard, капча). Попросите разработчиков добавить ваш IP в разрешённые или тестируйте стенд без защиты |
| Тест оформления: кнопка не найдена | Посмотрите список «Похожие элементы на этой странице» в Терминале или отчёте и впишите подходящую строку в `checkout.txt` |
| `npm error enoent Could not read package.json` | Терминал не в папке агента. Используйте команды из раздела 3 целиком — они начинаются с `cd ~/Documents/site-speed-checker &&` |
| Команда «молчит», а в конце `command not found` | Команда была введена в обратных кавычках `` ` ``. Введите её без них |
| `cd: no such file or directory` | Агент лежит не в `~/Documents/site-speed-checker` или в пути опечатка. Подставьте свой путь (раздел «Как вводить команды»), а путь с пробелами возьмите в кавычки |
| `Cannot find package 'playwright'` | Не выполнен `npm install` (раздел 1.3) |
| `Executable doesn't exist … chromium` | Браузер не скачался. Выполните `npx playwright install chromium` |
| `command not found: node` / `npm` | Не установлен Node.js (раздел 1.1) |
| `Не найден файл со списком страниц` | Нет файла `pages.txt` в папке агента |
| `npm error enoent Could not read package.json` сразу после `cd` без ошибок | Вы перешли не в ту папку: внутри нужной должны лежать `package.json` и `check.js` (проверьте командой `ls`) |
| В `npm run schedule:status` последний запуск «с ошибкой» | Откройте журнал, путь к которому показан там же, — в конце будет причина. На macOS см. также `reports/_schedule/launchd.log` и раздел 3.1 |
| `pages-test.txt, строка N: … не совпадает с тестовым доменом секции` | Адрес страницы не относится к домену из строки `[тестовый домен = прод-домен]` над ней — исправьте домен в скобках или адрес (раздел 2.5) |
| `🧪 Тест против прода: не удалось сравнить` | Тестовая или прод-страница не открылась: проверьте VPN/доступ к стенду и что такой путь есть на проде |
| `competitors.txt: группа «…» пропущена` | Нашей страницы из этой группы нет в `pages.txt` — добавьте её туда или исправьте адрес в `competitors.txt` (раздел 2.4) |
| `competitors.txt, строка N: …` | Ошибка в строке: адрес без `https://` или в группе нет страницы конкурента |
| `не найдена программа crontab` (Linux) | Не установлен cron — установите и включите его по таблице в разделе 3.1 |
| `npm run audit:checkout`: «не найдена кнопка «…»» | На сайте кнопка называется иначе или ещё не появилась. Откройте сайт, посмотрите точную надпись и впишите её в `checkout.txt` (раздел 3.2). Проверка без заказа — `npm run audit:checkout -- --check` |
| `npm run audit:checkout`: «после отправки не появилось поле для кода» | Сайт показал капчу или ошибку — посмотрите в окне браузера. Капчу пройдите сами и запустите тест снова. Если поле кода необычное, укажите его в `checkout.txt`: `поле кода = css: …` |
| `npm run audit:checkout`: «в корзине аккаунта уже есть товары» | Так бывает, если в `checkout.txt` стоит `удалять другие товары = нет`. Удалите товары из корзины на сайте и запустите снова. Если корзина пуста, а агент так пишет, — впишите в `checkout.txt` строку `пустая корзина = <текст, который сайт пишет в пустой корзине>` |
| `npm run audit:checkout`: «не удалось удалить из корзины: …» | На сайте другая кнопка удаления. Посмотрите кадры шага «Удаление других товаров» в отчёте и укажите в `checkout.txt` `удалить товар = …` (текст кнопки или `css: …`), при необходимости `меню товара = …` и `подтвердить удаление = …`. Или удалите эти товары на сайте вручную |
| `npm run audit:checkout`: «кнопка «Выйти» не найдена» | Сессия закрыта удалением cookies, но на сайте она может числиться ещё какое-то время. При необходимости завершите сеансы в личном кабинете; укажите в `checkout.txt` `выход = …` и `адрес профиля = …` |
| В отчёте при нажатии на ссылку в таймлайне: «Не удалось скопировать» | Браузер запретил копирование (так бывает в некоторых браузерах при открытии файла с диска). Полный адрес показан в том же сообщении — выделите его мышью и скопируйте `Cmd+C` (на Windows `Ctrl+C`). Сообщение держится 10 секунд |
| `В settings.txt не задано расписание` | Уберите `#` перед строкой `расписание = …` в `settings.txt` (раздел 3.1) |
| `settings.txt, строка N: …` | Ошибка в файле настроек: неизвестная настройка или значение не «да»/«нет» (раздел 2.3) |
| `budgets.txt, строка N: …` | Ошибка в файле бюджетов: опечатка в названии показателя или значении. Сверьтесь с разделом 2.2 (время — «с» или «мс» кириллицей, вес — «МБ» или «КБ») |
| `ключ CrUX API не подошёл` | В `crux-key.txt` опечатка или лишние символы. Скопируйте ключ заново (раздел 1.4) |
| `Chrome UX Report API не включён…` | Для проекта Google Cloud, где создан ключ, не включён Chrome UX Report API или ключ ограничен другими API (раздел 1.4, шаги 3 и 5) |
| Страница в отчёте с ошибкой `Timeout` | Сайт не открылся за 45 с или блокирует ботов. Попробуйте `--timeout=90000` |

## 7. Обновление агента

Код агента и эта инструкция лежат в открытом репозитории https://github.com/crabpipl/site-speed-checker. Папки `node_modules/` и `reports/`, а также личные файлы (`crux-key.txt`) в репозиторий не попадают (см. `.gitignore`): библиотеки ставятся командой `npm install`, отчёты создаются на том компьютере, где запускалась проверка.

### 7.1. Как получить последнюю версию

Если агент скачан через Git (раздел 1.2, вариант А):

```bash
cd ~/Documents/site-speed-checker && git pull && npm install
```

(`npm install` нужен, только если менялся `package.json`; если ничего не изменилось, он отработает за пару секунд.)

Ваши `pages.txt` и `settings.txt` обновление не трогает — их нет в репозитории. Правки в остальных файлах настроек (`budgets.txt`, `competitors.txt` и т. п.) тоже сохраняются. Если `git pull` пишет, что ваши изменения будут перезаписаны (`would be overwritten by merge`), значит, этот же файл обновился и в репозитории: сохраните свою копию файла, выполните `git checkout -- <имя файла>`, затем снова `git pull` и верните свои строки в обновлённый файл.

### 7.2. Можно ли менять агента

Изменять файлы у себя на компьютере можно как угодно — это ваша копия. Отправить изменения в репозиторий https://github.com/crabpipl/site-speed-checker может только его владелец: у остальных доступ только на чтение. Код распространяется по лицензии MIT (файл `LICENSE`): его можно использовать, изменять и распространять свои копии, сохраняя указание авторства.

| Сообщение | Решение |
|---|---|
| `fatal: not a git repository` | Терминал не в папке агента или агент скачан архивом, а не через Git — используйте команды целиком, с `cd ~/Documents/site-speed-checker &&` в начале |
| `would be overwritten by merge` при `git pull` | Ваш файл настроек изменился и в репозитории — см. раздел 7.1 |
| `CONFLICT` после `git pull` | Один и тот же файл изменён у вас и в репозитории. Откройте файл, оставьте нужные строки, удалите метки `<<<<<<<`, `=======`, `>>>>>>>`, затем `git add .` и `git commit -m "Мои настройки"` |
